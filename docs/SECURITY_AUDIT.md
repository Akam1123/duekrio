# Security audit — early access invoice workspace

**Reviewed:** 2026-09-25; release-status update 2026-09-26. **Scope:** the static React/Vite application, its CSV/JSON import and export paths, optional encrypted local workspace, checked-in GitHub workflows in the [public repository now named Orvaket](https://github.com/Akam1123/orvaket), the **earlier** Duekrio and Duenara Cloudflare Pages direct-upload releases built from commit `242c7879cd8af7a9ebc8882fcc2ce84489d2bd36`, and the legacy GitHub Pages response. Source tests, live page checks, and a full live encrypted-workspace regression passed on those earlier releases. Earlier intermittent raw-file verification timeouts led to a latest-attempt-wins fix; a deterministic race test passed on both then-deployed Cloudflare releases. The new [Orvaket release](https://orvaket.pages.dev/) is live and passed a **limited** direct-route, header/CSP, fictional-board, copy-action, mobile, 404, and automated-accessibility smoke check. That check does not repeat this entire audit or its full encrypted-workspace regression on the new origin; preserve that distinction. No independent penetration test or security review has been performed. This maps the 19 concerns in the [article supplied by the owner](https://medium.com/@madangopalboddu123/vibe-coding-got-you-hacked-here-are-the-19-vulnerabilities-nobody-warned-you-about-f0f899d61f78) to this product. The article is a source of audit topics, not an instruction to add features or claim that every example applies.

**Status key:** **N/A** means the vulnerable component does not exist in this release; it must be reassessed if the architecture changes. **Mitigated** means a specific control or absence was verified, not that exploitation is impossible. **Partial** means some controls exist and a residual risk remains. **Open** means a material exposure remains to address.

On 26 September 2026, compatibility deployments on both old Cloudflare origins were checked separately for `noindex` and migration guidance toward Orvaket. The Duenara deployment was `cd341ea4`; the [hosting record](HOSTING.md) has its URL and checks. Those checks did not repeat the full encrypted-workspace regression on Orvaket or inspect any visitor's saved invoices.

## Other controls and remaining priorities

- CSV upload is capped at 2 MiB. The import has a preview, reports skipped rows, requires acknowledgement of issues, and preserves existing data until confirmation. CSV export prefixes formula-like cells before writing spreadsheet files. These flows are in [App.tsx](../src/App.tsx) and [ledger.ts](../src/lib/ledger.ts). Spreadsheet programs can vary; users should still treat imported/exported files as untrusted.
- Corrupt browser data blocks edits and prompts for a raw download before restore or discard. Restoring a JSON backup validates it before replacing the workspace. Browser safety QA covered these paths, including an oversized backup and a valid restore.
- Optional exported-file and browser-workspace encryption use Web Crypto AES-256-GCM, a fresh 16-byte salt and 12-byte IV for each backup or encrypted save, and a PBKDF2-SHA256 key derived with 600,000 iterations from a user-entered passphrase of at least 16 characters. The browser key is nonextractable and kept in memory only while the tab is unlocked; the app does not save or recover the passphrase. Tests covered backup round-trip restore, fresh randomness, wrong passphrase, altered ciphertext, rejected envelope metadata, and local browser save/recovery paths. The full live encrypted-workspace regression and a separate deterministic raw-verification race test passed on the earlier checked release. A weak, reused, or exposed passphrase can still be guessed or stolen; an unlocked tab and exported CSV/plain JSON/raw recovery downloads remain readable. This code has not had an independent cryptographic review.
- GitHub [private vulnerability reporting](https://github.com/Akam1123/orvaket/security/advisories/new) was enabled and its new-repository setting read back as enabled on 2026-09-25. It is for software vulnerabilities, not customer data or privacy requests. On 2026-09-26, the user supplied an Israel-based individual display name and authorized contact email for the public privacy page. The email route's delivery and the full legal operator identity remain unverified.
- On the repository then named Duekrio (now Orvaket), GitHub vulnerability alerts, automated Dependabot security updates, secret scanning/push protection, and private vulnerability reporting were read back as enabled on 2026-09-25. [CodeQL's run for the earlier checked application release](https://github.com/Akam1123/orvaket/actions/runs/36185984290) completed its Actions and JavaScript/TypeScript analyses, and GitHub reported zero open code-scanning, Dependabot security, or secret-scanning alerts at that point. [Main CI](https://github.com/Akam1123/orvaket/actions/runs/36185984227) also passed. These are point-in-time scanner results, not a proof of no vulnerabilities. Earlier CodeQL findings in the **old** PromiseLedger repository were fixed at `bbc209f` after parsed exact-origin URL comparisons and least-privilege CI permissions were added. The checked-in [Dependabot configuration](../.github/dependabot.yml) schedules version-update PRs. Review future alert and scan findings; [GitHub's public-repository security guide](https://docs.github.com/en/code-security/getting-started/quickstart-for-securing-your-repository) explains these features.
- New JSON backups include the sample-data marker and pending reconciliation flags; legacy backups remain readable, although their omitted marker cannot be recovered automatically. A stale second tab is warned and its browser writes are paused when another tab changes the workspace. It can export its local copy before reloading the latest saved version. The browser test covered two tabs with an open invoice draft. Web Locks serialize writes where supported; older browsers still rely on the storage-event and preflight checks, so a simultaneous write race cannot be ruled out on every browser.
- The older PromiseLedger repository retains its **GitHub Pages** workflow and old site for migration; the repository now named Orvaket has no Pages deployment workflow. Neither of the two earlier Cloudflare Pages projects was connected to automatic GitHub deployment; the intended Orvaket project also requires its own verified deployment. Both Duekrio and Duenara received manual direct uploads of separately prepared, tested `dist-hosted/` builds from source commit `242c7879cd8af7a9ebc8882fcc2ce84489d2bd36` to their `main` production branches. A Git push alone does not update these Cloudflare Pages projects. [Direct Upload cannot be converted to native Git integration](https://developers.cloudflare.com/pages/get-started/direct-upload/); same-project CI would need a separate, reviewed API-token workflow. On 2026-09-25, GitHub `main` protection was read back as requiring a pull request and a passing `verify` check, applying to administrators, requiring linear history and resolved conversations, and disallowing force pushes and deletion. It requires zero approving reviews because this is currently a single-maintainer repository. Cloudflare account access controls and manual uploads still need ongoing review; repository checks cannot prevent a direct Cloudflare upload.
- The hosted build uses external JavaScript and CSS rather than executable inline HTML. Its generated `_headers` rule applies to `/*` on Cloudflare Pages static responses. Duekrio and Duenara live browser QA checked six pages, the 404 page, sample copy action, canonical metadata, 320–1440 px layouts, automated accessibility, and browser errors. Live HTTP checks returned 200 with the intended security and `noindex, nofollow` headers. A fresh-browser Duenara sample backup was restored on Duekrio. The full encrypted-workspace suite passed on Duekrio and the raw-file verification race test passed on both deployed hosts. Browser tests cover specific scenarios and do not prove every browser/device combination safe.
- Moving to a new hostname changes the browser **origin**. Existing `localStorage` entries on the old GitHub Pages, Duenara, or Duekrio Cloudflare origins will not follow to Orvaket automatically. Keep the old apps usable for export, and restore through a validated JSON backup on the new host. Keep the current storage keys and backup formats compatible through the visual rebrand. Never silently overwrite or assume that an empty new-origin workspace means the old data is gone. This follows from [MDN's origin](https://developer.mozilla.org/en-US/docs/Glossary/Origin) and [localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage) behavior.
- The legacy free GitHub Pages service is not intended or permitted for a commercial SaaS/online business under [GitHub's Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits). Cloudflare Pages Free is the primary host. Recheck its current terms, limits, and **actual response headers** after each deployment.

## Limits of this review

This was source review, dependency advisory lookup, local browser flow QA, live checks of the **earlier** Cloudflare page/header responses, CodeQL analysis, and the stated encrypted-workspace and migration browser scenarios. The new Orvaket release has a narrower live smoke check described above and in [HOSTING.md](HOSTING.md). This was not a penetration test, an exhaustive check of every response, malware scan of every dependency, audit of the user's computer or accounts, or legal opinion. No software or hosting choice can guarantee zero breaches, data loss, claims, or liability. Reassess the N/A rows before adding authentication, server storage, payments, email sending, analytics, or third-party scripts.
